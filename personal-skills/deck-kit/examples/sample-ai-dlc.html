02 · 痛点一 需求评级缺失

需求没有尺子，吞吐量只是一个形容词

真实卡片长这样
0715迭代需求 - 项目UX调整&状态流转UAT测试UAT 测试
0715迭代需求 - 交付物调整-功能测试功能测试
0729迭代需求 -【项目制】BPM 价值展示功能开发
V20260909 -【项目制】复盘功能测试验证功能测试
同一条需求被切成 N 张卡，粒度随人而定：拆分越细，卡数越多，越像干得多。
1不可加
卡数 ≠ 需求数。拆分粒度不同，卡数可以翻倍而交付内容不变。
2不可比
三个项目各算各的账：有的数卡、有的数工时、有的数版本，横向比不了，跨期也比不了。
3不可信
工时估得其实挺准（整体偏差 -3.1%）——但工时是成本，不是交付规模。用成本证明产出，逻辑不成立。
所以先说清楚一件事：没有统一的「大小」，就没有统一的「吞吐」；没有吞吐，「提效 20%」既无法证明，也无法被审计。

05 · 关键设计 让链路自己长出来

可观测性来自数据结构，不来自额外流程

把度量需要的信息，塞进本来就该写的地方—— 文档头、文件名、提交信息。度量变成副产品，没人需要额外交表。
每份产物开头的 trace 块
--- trace: schema_version: sdlc/v1 artifact_id: REQ001-2104 # 挂哪张卡 parent_artifact_id: — # 父需求卡 artifact_type: prd # prd/story/… dir: 2-planning/req-20261014.01/prd version: req-20261014.01 upstream: [../prd/prd-….md] # 上一环节 created: 2026-09-03 10:00:00 # 阶段完成 ---
一个 created 时间戳之差，就是阶段 Lead Time——不需要任何人回忆「这事什么时候做完的」。
① 文档名带 Key
人眼可追：prd-REQ001-2104-考核待办.md
② 文档头贴 trace
机器可读：谁是谁的上游、属于哪个版本、什么时候完成，一次扫盘就能重建链路台账。
③ 提交信息带 Key
需求 ↔ 代码自动关联：[REQ001-2186] feat: 新增审批接口
三条约定合起来，「需求 → 架构 → 代码 → 测试」全链路跟踪，无额外维护成本。

给需求一把能对外解释的尺子

国际标准 COSMIC 功能点（ISO/IEC 19761）：数一条需求有多少次「数据移动」， 再把刻度锚到一个所有人都看得懂的基准上——一个标准 CRUD 页面。

每类数据移动计 1 CFP；一条需求的全部数据移动求和，就是它的功能规模。
结构定规模、成本另算：当量与工时解耦，同一把尺子量所有团队。

三条红线：结构定规模（工时免疫）· 尺子只有一把 · 成本单独换算。

三条与结构尺同源的纪律
1AI 只列项，不填小时
估工时是判断不是测量，换模型就漂。实测：自由填小时卡间离散约 29%，走带值表收窄到约 10%。
2带值表是团队属性
表里的 M 值由本团队真实卡片校准。跨团队只比当量，不比工时；换表必升版本号，全批重跑。

隐含生产率 = Σ开发工时 ÷ Σ当量。与团队历史比，能分清是「刻度不准」还是「排序不准」——这是双尺最大的价值。

08 · 怎么证明 真提效 vs 感觉快了

什么才算真提效：三个指标，两个陷阱

有了两把尺子，才谈得上「证明」。判断标准只有一条：把需求大小归一之后，再看速度与成本—— 不是看大家有多忙，也不是看工时填了多少。
三个真信号（同口径 · 前后对比）
1单位当量交付周期 ↓
同样大小的需求，从开工到完成更快。分子是自然日，分母是当量——需求大小被归一，快慢才可比。
cycleDaysPerStandardReq
2每迭代交付当量 ↑
同样长的时间，交付的「标准需求个数」更多。这是吞吐的北极星，不是卡数、不是任务数。
Σ PRD requirementEquivalent / iteration
3工时 / 当量 ↓
同样的产出，投入更少。AI 真正压下来的是这块成本，而不是让人加更多班。
hoursPerStandardReq
两个陷阱（看着像，其实不是）
✕ 卡数 / 任务数上升
拆分粒度一改，卡数就能翻倍。用卡数证明提效，等于用「拆得更细」证明「干得更多」。
✕ 工时填报下降
可能只是少填了。工时是成本单位，必须配合「当量吞吐」一起看；单看会得出反的结论。
稳定器：估算准确度。提效不能靠「每次都延期」换——P80 命中率不明显恶化，结论才站得住。
结论写法：「本迭代交付 16.20 当量，单位当量周期 4.65 天」，而不是「团队效率提升 30%」。
指标口径：需求当量度量 + 迭代仪表盘

09 · 解法二 测试内核

测试不靠「人手写」，靠「按 AC 生成 + 机器核对」

Lilian 是交互层，测试内核换成了 BMAD TEA（Test Architecture Enterprise）：把「风险 → 设计 → 证据 → 发布门禁」 做成一条工程链路，每一步有产物、有判据、有人工确认点。

三条比「写用例」更硬的约束
1声明不算证据
标题里写了 AC 不算数。断言没有真正命中这条 AC，就进 rejectedEvidence——覆盖是核对出来的，不是标注出来的。
2严重度不靠评审人拍
35 条准则固定分级，评审只负责对号入座。CRITICAL 扣 10 分且封顶 69，直接 Block；四路（确定性/隔离性/可维护性/性能）并行打分再聚合。
3豁免只能人签
覆盖率数据推不出 WAIVED。必须人签，并写清理由、期限、监控与整改人。门禁阈值：P0 100%、P1 ≥90% 才 PASS。
Agent 干：读 PRD / 架构 → 算风险分 → 拆场景选层 → 生成并执行 → 修测试自身缺陷
人只干三件：批策略与用例 · 定缺陷归属 · 签豁免

10 · 用例与脚本 为什么用 PyTest BDD

用例先让人能达成共识，脚本才让机器能反复执行

我们让 TEA 按 PyTest BDD（Given / When / Then） 写用例：产品、QA、开发读同一份文本就能对齐； 同一份用例再生成 pytest-bdd 场景与 step 实现——人只需要审一件事：这条 AC 有没有被准确覆盖。

Feature: 复盘签批 Scenario: 签批通过后状态自动流转 [AC-3] Given 项目已推进至 "completed" When 提交复盘签批并通过 Then 项目状态应为 "reviewCompleted"

业务读 Given / Then，开发读 step，QA 审覆盖——同一份文本，三种角色各自能读。
从用例到脚本：三步映射
1一条 AC → 一个 Scenario
Scenario 标题带 AC 编号，覆盖关系可被机器统计，不靠人写覆盖矩阵。
2每句 GWT → 一个 step
step 实现可复用：Given 建状态、When 做动作、Then 断言，跨需求共享同一批 step。
3数据准备写进 step，不写进用例
用例只描述业务状态；建数、清理、等轮询都在 step 里完成——用例因此短、稳、可读。
人审就三问：这条 AC 被覆盖了吗？边界与负向有吗？断言验到的是业务结果吗？

11 · 可借鉴 架构师视角的六个模式

能带走的不是工具，是六个设计选择

客户会换、工具会换、模型半年一迭代。下面六条与具体产品无关，换到任何一个交付团队都成立。
1主键先行
先定义能贯穿「需求→文档→代码→测试」的唯一 ID，再谈自动化与度量。没有脊柱，所有报表都是估出来的。
反例：靠文件夹猜归属，三个月后没人说得清哪行代码属于哪个需求。
→ 落地：卡片 Key + trace + commit 前缀
2尺子先于工具
口径不定，工具只会放大噪音。优先选能对外解释的标准，而不是自研一套只有自己人懂的公式。
反例：自研评分公式，每次跨团队汇报都要重讲一遍算法。
→ 落地：COSMIC 当量 + 两层尺子
3确定性归程序，不确定性归 AI
AI 负责从非结构化文档里抽取事实，程序负责求和与换算。
好处：换模型、换提示词，历史数字都不用重算，跨期可比。
→ 落地：AI 数数 + 脚本算当量
4红线写进代码
「没有证据不评定」「没有批准不出脚本」，写成门禁而不是倡议。
反例：靠自觉的规范，第二周就退化成「这次特殊，先过吧」。
→ 落地：双证据源门禁 + 用例硬门禁
5Agent 提速「生成」，回归交给流水线
Agent 解决的是用例与脚本的生成效率；脚本一旦产出，回归就是自动化执行，不再依赖 Agent。
反例：只给 QA 配个 Copilot，写用例快 20%，脚本还得手写，端到端没变。

12 · 小结 三句话与三个动作

AI 提效的瓶颈，很少在模型能力

更多时候在度量口径与组织交接面。这两件事都不性感，但它们决定了 AI 的收益能不能被看见、被承认、被复制。
回到团队，可以马上做的三件事
1挑一条真实需求，先给它一个贯穿全链路的 ID
不用等平台改造。文档名、文档头、提交信息三处对齐，一天就能试。
2定一把尺子，选标准不选自研，先量一个迭代
量出来的第一个数字一定不准——没关系，口径统一比数字精准更重要。
3找端到端最堵的那一段，问「这里谁负责」
如果答不上来，那就是瓶颈——通常也是收益最大的地方。

谁在等谁、等多久，这件事有人算过吗？
别一次全做。先把第一件事做出一个数字，再谈第二件——顺序反了，三件事都会变成文档。
