# 编写可执行计划

计划的作用是消除实现者必须猜测的关键内容，而不是把每个命令展开成流程仪式。先定义连贯成果和验收边界，再固定高熵实现决策、选择验证方式，最后才安排依赖和并行。

计划默认保存到 `docs/plans/YYYY-MM-DD-<feature-name>.md`；用户指定路径时以用户为准。

## 判断是否需要计划

以下情况通常需要计划：

- 多个有依赖关系的实现步骤
- 跨模块、跨服务或多类产物
- 需要协调多个 worker、迁移或外部副作用
- 用户明确要求书面计划

目标明确、局部、低风险且只有一个直接实现动作时，不要为了使用本 skill 强制生成计划。简要说明它不需要独立计划并返回实现即可；用户明确要求计划时，可以生成精简的单 Task 计划。

## 输入与门禁

优先使用用户给出的精确 spec 路径，其次使用当前对话明确批准的设计。存在 spec 时读取其 `Spec Revision`、`Spec Approval Revision` 和 `Review Mode`，只有批准版本相等才能基于它写计划；`review` 模式还要求 `Independent Review` 为当前 revision 的 `reviewed revision N`（仅 FULL 审核）或用户明确的 `skipped-by-user revision N`，`no-review` 模式要求 `not-required`。计划必须原样复制 spec 的 `Review Mode`，不得在计划中另行选择。来源内容在计划批准前发生实质变化时重新生成受影响部分。

没有 spec 时，只要需求、约束和验收已经明确，或用户明确选择跳过正式设计，就可以继续。在当前对话尚未确定 `Review Mode` 时，先按复杂度推荐 `review` 或 `no-review`，让用户选择后再写计划。在计划中写一个简短的“实现依据”章节，不要制造虚拟 spec 状态；无 spec 路径也必须在计划中持久化用户选择。

发现缺失的产品、UX、数据、安全或公共接口决策时，停止并返回 `brainstorming`；实现细节可以在不改变用户意图的前提下由计划确定。

## 计划边界

一份获批 spec 默认生成一份执行计划。多步骤、跨模块依赖和并行机会应在该计划内部通过 Task、DAG 和 Wave 表达。

只有来源已经拆成多份独立获批 spec，或用户明确要求分别规划，并且每个子项目都能独立交付、批准和验收时，才生成多份计划。每份计划分别绑定自己的来源与批准；不要从一份 umbrella spec 自动创建多份相互依赖的计划，也不要构造跨计划 DAG、Wave 或统一执行顺序。若多个成果不能独立验收，或依赖另一计划的中间状态，保留为一份计划；来源设计边界需要改变时返回 `brainstorming`。

## 计划详细度

计划详细度独立于 `Review Mode`：

- `standard`：默认。记录精确文件与符号、现有锚点、关键契约、行为分支、接线点、代表性案例和验证，不展开普通样板代码。
- `guided`：用户明确要求计划更详细，或任务包含易错的跨模块接线、状态转换、迁移、安全/权限、并发、幂等或兼容逻辑时使用；额外提供关键代码骨架、调用顺序、输入输出样例、测试断言和禁止偏离项。

用户指定时采用其选择；否则默认 `standard`，复杂任务可选择 `guided` 并记录理由，无需单独询问。详细度、关键实现契约或 Task DoD 变化时按实质计划修订处理。

两档都只展开影响正确性的内容：不复制可从现有代码唯一推导的实现，也不把计划写成完整 patch。

## 提交策略

在计划完成前确认一次 `Commit Policy`：

- 用户明确要求不提交：使用 `no-commits`，不再询问
- 用户明确要求提交：使用 `wave-commits`，不再询问
- 用户未表态：询问一次，默认选项为 `wave-commits`

只有针对该提交问题的明确回复才算确认；用户在看到选项后直接回复“继续”或“按默认”，可视为选择默认。把选择和来源写入计划。

- `wave-commits`：主 agent 在验证通过的 Wave 边界提交连贯改动。通常每 Wave 一个 commit；最后一个 Wave 的提交延迟到 implementation review、repair 和最终验收之后。实现审核后的代码修复使用 `repair-commit`，最终验收状态写入运行状态；不创建只包含状态的 finalization commit
- `no-commits`：不创建 commit，也不生成 patch、evidence 或 boundary 替代工件

Wave 是依赖和调度边界，不应为了满足提交数量反向改变 Task 拆分。

## Task 拆分与并行

目标是缩短依赖关键路径，不是增加 Task 数量。Task 应是值得占用一次完整 worker 上下文、并拥有独立 DoD 的最小连贯成果。

Wave 是依赖和调度边界，不等于必须启动新 worker。委派会产生 Task Packet、项目上下文和相关文件的重复加载成本；只有隔离、并行或独立验收收益高于该成本时才拆 Task 或使用独立 worker。单一低风险 Task 建议主 agent 直接执行；连续步骤共享大量上下文、文件和同一验证闭环时应合并为一个 Task。确需保留为相邻串行 Task 且宿主支持续接 worker 会话时，建议复用同一 worker，不要为了形成多个 Wave 反复启动新会话。

1. **定义连贯成果**：一个 Task 交付一个可以独立解释、独立验收的结果。
2. **识别共享前置**：找出接口、schema、类型、生成规则和运行资源。
3. **寻找并行边界**：优先考虑不同子工程、独立模块、平台适配，以及不依赖最终实现细节的文档。
4. **建立依赖 DAG**：共享契约先行，后续消费者并行，最后安排集成验证。
5. **安排 Wave**：把依赖已满足、边界可隔离且有并行净收益的 Task 放在同一 Wave。
6. **记录执行建议**：标注建议执行方式和并行理由；实际调度由 `executing-plans` 决定。

需要相同上下文、属于同一验证闭环或不能独立验收的修改应合并。不要按文件、命令或 TDD 步骤拆分；只有并行收益足以覆盖上下文加载、委派和集成成本时才拆分。并行 Task 必须避免写入覆盖和共享资源冲突，也不能读取另一个 Task 尚未完成的中间状态。在共享工作树中以文件为最小写入所有权边界；同一文件只能由一个 active worker 修改。符号级拆分只有在独立 worktree/sandbox 中才允许。

## 实现充分性门禁

写计划前读取每个目标区域最相关的现有实现和测试，记录可复用模式。不要只根据 spec 猜测文件名、符号、命令或框架习惯。greenfield 区域没有现有锚点时明确写“新建契约”，并以获批 spec、项目级约定和已核实的框架/API 文档为依据，不得虚构参考文件或符号。

把会影响行为正确性、且无法从指定现有锚点唯一推导的内容视为**高熵决策**。以下相关项必须由计划固定：

- 公共或跨 Task 使用的类型、函数签名、组件 props、事件、API、schema 和配置键
- 正常、空值、失败、权限、冲突、重试和重复执行等关键分支的结果
- 错误类型、状态码、错误映射、事务边界、状态转换、并发和幂等规则
- 新代码的调用方、注册、导出、依赖注入、路由、迁移和跨模块接线位置
- 至少一个代表性正常案例，以及一个会改变实现方式的重要失败或边界案例
- 必须沿用的现有实现模式，以及明确禁止的兼容层、抽象、依赖或范围外改动

若实现者仍需自行发明上述任何相关决策，计划尚未完成。若这些内容属于产品、公共接口、数据或安全决策且来源未确定，返回 `brainstorming`；若只是实现细节，计划作者在不改变用户意图的前提下确定并记录。

普通 CRUD、样板 JSX、简单字段映射和可从明确现有锚点唯一推导的代码不需要展开。对这些内容给出精确锚点和差异即可，例如 `src/orders/create.ts:createOrder`，并说明复用哪个模式、改变什么；greenfield 则说明新建边界和约束来源。

## 按场景选择验证策略

TDD 是适合特定任务的实现技术，不是所有计划的固定模板。

| 场景 | 默认策略 | 计划中应写的证据 |
|------|----------|------------------|
| 业务逻辑、算法、可复现 bug | 测试驱动 | 能因目标行为而失败的聚焦测试、实现后通过、相关回归 |
| Parser、校验、稳定 API 合约 | 测试驱动或契约测试 | 输入输出、错误边界和回归测试 |
| UI 交互逻辑 | 混合验证 | 组件/E2E 测试，加浏览器和可访问性检查 |
| 纯样式、布局、视觉调整 | 验证驱动 | 浏览器视口、截图或人工视觉检查，不强制制造失败测试 |
| 配置、CI、IaC | 验证驱动 | schema、lint、dry-run、构建或 smoke test |
| 文档 | 验证驱动 | 文档构建、链接、示例、渲染和内容检查 |
| 数据迁移 | 验证驱动 | 隔离环境中的迁移前后断言、重跑、rollback 或 forward-fix |
| 机械重构、rename、依赖升级 | 回归驱动 | 修改前基线、搜索、typecheck、构建和既有回归；通常不新增人为 red |
| 外部服务集成 | 混合验证 | mock/contract 测试，加 sandbox/canary smoke 和清理步骤 |
| 缺少测试设施 | 验证驱动 | 定向复现、构建、静态检查和人工 smoke；建设测试设施作为单独范围决策 |
| 方案或可行性未知 | 探索验证 | 时间盒、假设、实验结果和决策门；结论产生后再计划依赖它的实现 |

选择测试驱动时，失败必须来自目标行为尚未满足，而不是故意制造语法错误或不存在的符号。Red、Green 和必要重构属于同一 Task 的内部过程，不需要分别成为计划复选框。

## 并行与 Wave

多 Task 计划才需要在文档中列出 Wave。单 Task 在执行语义上等同于隐式 `Wave 1`，但不因此强制委派。`Wave 1` 包含没有未满足依赖、并且并行收益高于协调成本的 Task；后续 Wave 依此类推。

同一 Wave 并行前检查：

- 写入文件范围不会互相覆盖；共享工作树禁止两个 Task 修改同一文件
- 一个 Task 不依赖另一个 Task 的中间实现
- 测试、构建、formatter、端口、数据库、缓存和生成目录可以隔离
- 所需共享契约已经稳定
- 并行节省的时间值得额外上下文和集成成本

无法满足时可以有意串行，不需要把“没有最大并行”视为计划错误。需要跨 Task 接线时，优先把接线归入拥有该连贯成果的 Task；只有它本身形成清晰成果和验收边界时才创建独立集成 Task。

验证责任按一个 Wave 的实际执行者数量确定：单 worker Wave 由该 worker 完成 Task 验证和该 Wave 的完整验证；多 worker Wave 由各 worker 完成各自 Task 验证，主 agent 只运行跨 Task 接线、构建或集成检查。计划不要安排主 agent 在单 worker Wave 后机械重跑同一组命令。若整份计划只有一个 Task/一个 Wave，且 Wave 验证完整覆盖最终验收，应在“最终验收”中明确声明两者等价，避免执行器重复运行；多 Wave 计划仍保留计划级最终验收。

## 计划头部

```markdown
# [功能名称] 执行计划

**目标：** [一句话说明可见结果]
**来源设计：** [`path`，revision N；无正式 spec 时写“无，见实现依据”]
**计划版本（Plan Revision）：** `1`
**计划批准版本（Plan Approval Revision）：** `none`
**审核模式（Review Mode）：** `review | no-review`
**独立审核（Independent Review）：** `not-requested`（`review`）或 `not-required`（`no-review`）
**计划详细度（Plan Detail Level）：** `[standard | guided]，理由：[默认 | 用户明确要求 | 复杂度理由]`
**提交策略（Commit Policy）：** `[wave-commits | no-commits]，来源：[用户明确选择 | 用户确认默认]`

**最终验收：**
- [ ] [可执行、可判定的用户或系统行为]
```

计划只保存稳定设计和任务信息，不保存 `Execution State`、`Resume Point`、`Execution Blocker`、临时目录或 worker lease。运行时进度由执行器维护；Task 复选框只在对应实现和验证完成后更新。

`Independent Review` 使用 `not-required`、`reviewed revision N` 或 `skipped-by-user revision N`；旧计划的 `not-requested` 只可作为未完成的 `review` 状态。`reviewed revision N` 只表示 reviewer 针对 FULL 范围看过送审时 revision，不表示主 agent 修复后的 revision 已被复审；`FOCUSED_SCOPE` 审核不能单独作为整份 revision 的门禁完成。`review` 模式批准前必须满足当前 revision 的审核门禁。任何改变计划详细度、关键实现契约、Task、依赖、验收或行为的修改都递增 `Plan Revision` 并把批准版本清为 `none`；受影响 Task、所有依赖后继和最终验收必须重置为未完成，并记录 `完成版本`。对已产生的非幂等副作用优先增加纠正 Task，不自动重跑原 Task。格式、复选框和提交结果更新不递增 revision。

## 必备章节

```markdown
## 实现依据
[来源 spec 的关键约束；没有 spec 时写已确认需求、范围和验收。]

## 实现策略
[文件/模块边界、总体顺序、现有实现锚点和关键差异。]

## 关键实现契约
[用 `C1`、`C2` 编号定义后续 Task 共享或容易猜错的接口、schema、行为表、错误语义、状态转换、接线点、代表性测试和禁止偏离项；简单计划也要说明完全沿用的现有锚点及唯一差异，greenfield 则说明新建契约及约束来源。]

## 任务与依赖
[多 Task 时用表格列出 Task、依赖、Wave、建议执行方式和并行理由；单 Task 可省略 Wave 表。]

## 执行任务
[按依赖顺序写 Task。]

## 最终验收
[完整命令、预期结果和必要人工检查。]
```

## 关键实现契约模板

每个契约只保留相关字段，但必须让后续 Task 无需重新决定行为：

````markdown
### C1：[契约名称]

**现有锚点或新建依据：** `path:symbol/section`，[复用的模式和本次差异；greenfield 写获批 spec、项目约定或已核实文档]
**调用方与接线位置：** [谁调用、在哪里注册/导出/注入，以及调用顺序]
**必须保持的接口或数据形态：**

```ts
[准确签名、类型、schema 或配置形态；只展示高熵部分]
```

**行为规则：**

| 条件 | 结果 | 副作用/错误 |
|------|------|-------------|
| [正常条件] | [返回或状态] | [写入、事件或无] |
| [失败/重复/边界条件] | [返回或状态] | [错误类型、状态码、不得发生的副作用] |

**代表性测试：** [fixture、调用和关键断言；可引用具体 Task 中的案例表]
**禁止偏离：** [不得改变的接口、行为、依赖或范围外事项]
````

`standard` 可以在现有锚点能够唯一确定普通代码时省略代码块，但行为规则和差异仍要明确。`guided` 对关键签名、schema、状态转换或编排顺序应给出可直接采用的小段骨架。

## Task 模板

只保留有信息量的字段。不相关的字段直接省略，不要填一串“无”。

```markdown
### [ ] Task N：[连贯成果]

**目标与范围：** [完成后成立什么，不做什么]
**涉及文件与符号：** [精确路径加目标符号/章节；同时声明共享工作树中的文件级独占范围]
**必读上下文：** [精确 `path:symbol/section` 及读取目的；只列实现当前 Task 必需的内容]
**引用契约：** [关键实现契约的 `C1`、`C2`；执行 dispatch 时必须内联相关正文]
**依赖：** [Task ID 或无]
**建议执行方式：** [主 agent 直接执行 | 独立 worker | 复用前一 Task 的 worker 会话；只有存在委派或协调理由时才写]
**并行边界：** [可并行 Task、稳定契约和隔离资源；仅准备并行时写]
**依赖与接线点：** [调用方、注册/导出/路由/注入/迁移位置，以及必须先后发生的步骤]
**Wave 验证责任：** [单 worker：该 worker 执行 Task 与 Wave 全部验证 | 多 worker：worker 执行 Task 验证，主 agent 执行跨 Task 集成验证；仅在有独立 Wave 验证时写]

**实施要点：**
- [相对现有锚点的具体差异、关键控制流和变更顺序]

**关键代码骨架：**
[仅写高熵部分。`guided` 应补充关键签名、分支或调用顺序；`standard` 在契约不能仅靠文字精确表达时填写。不要粘贴完整实现。]

**行为与测试案例：**

| 场景 | 输入/准备 | 预期结果或断言 |
|------|-----------|----------------|
| [代表性正常场景] | [具体输入/fixture] | [可判定断言] |
| [重要失败或边界场景] | [具体输入/fixture] | [错误、状态或副作用断言] |

**禁止偏离：**
- [不得改变的接口、行为、依赖或范围外事项；没有实际约束时省略]

**验收标准：**
- [可判定结果]

**验证策略：** [测试驱动 | 验证驱动 | 混合验证 | 探索验证，以及选择理由]
**验证：**
- `[精确命令或人工步骤]`，预期 `[结果]`
**完成版本：** [已完成 Task 填写 `Plan Revision N`，未完成省略]

**副作用与恢复：** [仅迁移、外部系统或非幂等操作需要；说明清理、回滚、forward-fix 或中断后阻塞]
```

`关键代码骨架` 只覆盖高熵实现形态，语法、名称和前后契约必须一致；可以省略明确不变的周边代码，但不能用 `TODO`、`自行处理错误`、`类似现有实现` 代替关键分支。共享内容只在“关键实现契约”定义一次，Task 通过 ID 引用；`executing-plans` dispatch 时负责内联，避免遗漏跨章节约束。

每个行为型 Task 至少包含一个代表性正常案例和一个重要失败或边界案例。纯样式、纯文档、机械重构等不适用时，改写为对应的视口、渲染、搜索、构建或回归案例，不制造虚假的输入输出测试。

## 自检与可选审核

保存前检查：

1. 每个需求是否映射到 Task 和验证，是否存在范围蔓延。
2. Task 是否按连贯成果拆分，而不是按命令、文件或 TDD 步骤机械拆分。
3. 每个 Task 的验证策略是否适合场景；不应有的 TDD 是否被移除。
4. 依赖 DAG 是否无环，Wave 是否安全且有实际并行收益。
5. 验收是否包含精确命令、可观察状态或人工步骤及预期结果。
6. 只有存在真实外部副作用的 Task 才要求恢复策略。
7. 提交策略是否已由用户确认，但没有反向支配 Task 边界。
8. 每个高熵决策是否已在关键实现契约或 Task 中固定；实现者是否仍需发明接口、分支、错误、状态转换或接线位置。
9. 计划引用的文件、符号、命令和现有模式是否已从当前代码库核实；greenfield 是否明确新建依据，而不是根据命名习惯虚构锚点。
10. `guided` 计划是否提供足够的代码骨架、调用顺序、样例和断言，同时没有退化成完整 patch；`standard` 是否仍包含必要契约，而不是任务清单。

`review` 模式使用 `plan-document-reviewer-prompt.md` 做一轮审核，由主 agent 根据审核结果修复并自检；不自动派发复审。审核完成后把送审时 `Plan Revision` 写入 `Independent Review`；若 reviewer 不可用，必须由用户明确选择稍后审核或 `skipped-by-user revision N`。`no-review` 模式只做主 agent 自检并写 `not-required`。普通单 Task 或低风险计划通常推荐 `no-review`。

## 批准与交接

让用户审核实际计划文件。`review` 模式先满足当前 revision 的审核门禁；用户明确批准当前 revision 后，把 `Plan Approval Revision` 写成当前 `Plan Revision`。用户要求实质修改时，递增 revision、清空批准版本并重置受影响 Task。

计划批准后，建议使用 `executing-plans`。不要自动开始实现；由用户决定何时继续。
